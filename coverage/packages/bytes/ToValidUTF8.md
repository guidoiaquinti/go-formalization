I checked the Go 1.27.0 scan against the model. The first malformed byte in a run emits the replacement bytes, and later bytes in that run emit nothing. ASCII and valid multibyte sequences each end the run. A valid encoding of U+FFFD remains intact. The replacement may itself be malformed and is copied byte for byte. Go makes a nonnil output and starts with capacity `len(input)+len(replacement)`.

The native comparison covers 4,216 boundaries and 60,000 samples using seeds 17, 2718 and 65537. The forward rune-range oracle distinguishes a valid U+FFFD from a malformed byte and independently checks output and the capacity policy stated in the record. Go and Lean compare the exact initial capacity when the output fits. Once growth is needed, the model records that fact and the driver checks that the resulting capacity covers the output length.

Exact post-growth capacity is observable and remains outside the Lean claim. On darwin/arm64, an input of `"\xffx\xff"` with replacement `"12345678"` produces length 17 and capacity 24. Adding another `"x\xff"` gives length 26 and capacity 32. Clamping these capacities to 17 and 26 would still pass the scoped growth comparison. The reviewer control checks their native capacity against separate append sequences with the intended chunk sizes. Exact allocator growth and backing identity remain outside the model.

Twelve independent native and Lean fixtures passed. Emitting one replacement per malformed byte fails two fixtures. Sanitizing the replacement bytes fails two. Returning nil for an empty output fails three.
