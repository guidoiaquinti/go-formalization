Go selects the high 16 bits when the word is at least 2^16, adds 16 for that shift, then applies the eight-bit threshold and generated byte-table lookup to the retained half. Otherwise the entire value fits in the low 16 bits. Lean factors those steps into `len16` with the same shift offset and byte model. The fixed Go entry point receives a uint32 on the 64-bit host. The kernel-checked theorem characterizes the result by the fit criterion for every candidate width and includes width zero for input zero. [Pinned implementation](https://github.com/golang/go/blob/go1.27.0/src/math/bits/bits.go#L324-L334) · [Table generator](https://github.com/golang/go/blob/go1.27.0/src/math/bits/make_tables.go#L85-L91)

On Go 1.27.0 darwin/arm64, the registered Go and Lean comparison passed 130 boundary cases and 60,000 samples with seeds 17, 2718, and 65537 in each build mode. The comparison checks an independent repeated-division oracle under default compilation and with intrinsics disabled in both the driver and `math/bits`. The pinned compiler registers `Len32` and `Len64` as arm64 intrinsics and aliases `Len` to `Len64` on 64-bit targets. [Compiler registration](https://github.com/golang/go/blob/go1.27.0/src/cmd/compile/internal/ssagen/intrinsics.go#L1010-L1055)

The shared control checked the exact fit criterion at each width from zero through the word width, including shifts at 64. Both sides are true at larger widths because the input fits in the machine word and the result is bounded. The real Go entry point passed every case in both build modes. Truncating to the low half failed 80 of 130 cases, and substituting population count failed 93 of 130. For example, input `0x00010000` requires 17 bits. Dropping the upper half returns zero and population count returns one. [Reviewer control](controls/WideLength/main.go)
